Extraction experiment · 24 Sep 2026

One-pass span extraction beats the distilled LLM on held-out sources

We adapted the “System One” decision-model idea (every schema field answered in a single forward pass, nothing generated) to named-field extraction. On documents from sources it never trained on, it is more accurate than our released generative student and several times cheaper to run.

What it does

Point at the text instead of writing it

A generative model reads the document and then writes a JSON answer one token at a time. The span model reads the document once and, for every field in the schema, points at where the answer starts and ends. If a field is not printed, it points at a “null” slot. The highlighted text below is one real held-out document header; the model got all nine fields right on it.

A small decoder picks the most likely span per field (or null), cuts it out of the document, and applies a normaliser chosen by the field’s declared type: dates to ISO, numbers from digits or roman numerals, text kept as printed. Each value also carries a calibrated confidence.

Architecture

One packed sequence, one branch per field

The backbone is Qwen2.5-1.5B with a rank-16 LoRA adapter, following the open kev reproduction of TypeSafe’s Jev. Each schema field becomes a short branch appended after the document: the field name, the description the user wrote in the schema, and a decision marker. The field descriptions come straight from the schema, so nothing about the domain is built into the model.

document tokens (first 1,536) date: …▸ number: …▸ place: …▸ … 6 more

Attention mask. Each branch sees the whole document and itself, never another branch, and all branches restart their positions right after the document. So the fields are answered in parallel, and adding a field only adds its own branch tokens. A start-up check confirms that editing one branch moves another field’s output by exactly 0.

  1. Each branch’s decision marker is projected into a start query and an end query.
  2. Both are scored against every document token (a pointer head), plus a learned null score.
  3. Softmax, a temperature fitted on development sources, then the best start–end pair against null.

Gold review

Every mismatch was read against the document

We reviewed each held-out field where either model disagreed with the labels. Thirteen labels were wrong or ambiguous: values not printed anywhere (an inferred settlement), a session ordinal stored as the act number, a budget code glued onto a number, four malformed dates such as 2025-12-грудня and 2025-04-??, two synthesised titles and one stale correction row. The corrections are kept in the experiment and have not been written back.

Span model errors
  • Cuts 105/105-style numbers to 105 in one unseen template
  • Returns null for a printed settlement or parent number in unfamiliar layouts
  • Title boundaries: stops early or runs into body text
  • Returns the inner title where labels expect the full heading of an explanatory note
Generative model errors
  • Unparseable output on 7% of units, losing all nine fields at once
  • Invented dates such as 2026-01-01 on pages without one
  • Titles translated into English
  • Wrong month; registration suffixes dropped

The generative failures are ones the span model cannot make by construction. We also found a scoring bug: the text matcher uses Python’s SequenceMatcher with autojunk on, which scored one correct 260-character title at 0.015 instead of 0.98.

Cost and speed

No decoding means fewer, cheaper GPU seconds

Both models read a similar number of tokens for a typical document, so reading costs about the same. The difference is everything after: the generative model writes around 180 tokens per window, sequentially, and repeats the whole read for every 4,096-token window of a long document. The span model does neither.

Limits

What it cannot do yet

  • It reads the first 1,536 tokens of a document. That covers 99% of labelled values here; longer documents need windowing.
  • It can only copy text that is printed. Values the labels reformat or synthesise need a normaliser rule or are out of reach.
  • No list fields yet, such as a roster of voters. Those still need the generative model or a multi-span extension.
  • One task and 59 held-out units so far. The margin over the baseline should be confirmed on other tasks.
Next

Proposed next steps

  • Repeat on a second extraction task and add multi-span output for list fields.
  • Build it as the distiller’s token_classifier backend, which is already declared but not implemented.
  • Benchmark both models on the same GPU with batching, using the released adapter.
  • Fix the autojunk scoring bug and push the reviewed labels back into Studio.
